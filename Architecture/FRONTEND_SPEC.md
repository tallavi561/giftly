# Giftly — מסמך אפיון Frontend

**נכון לתאריך:** 2026-08-12 · **ענף:** `master`/`main` (לאחר מיזוג `gemini-ux-ui`)
**מסמך זה מתאר את מצב ה-Frontend הקיים בפועל בקוד** — לא תכנון עתידי (למעט פרק מיוחד בסוף).

---

## 1. סקירה כללית וטכנולוגיה

Giftly היא אפליקציית web (RTL, עברית) שעוזרת למצוא מתנות לאנשים קרובים באמצעות AI, על בסיס תחומי עניין ואירועים (ימי הולדת, ימי נישואין וכו').

| רכיב | טכנולוגיה |
|---|---|
| Framework | React 18.3 + TypeScript, בנוי עם Vite 5 |
| ניתוב | react-router-dom 6.27 |
| Backend/DB | Supabase (Postgres + Auth + Storage) — נקרא ישירות מה-frontend (Auth, Storage) וגם דרך REST API עצמאי (`backend/`) |
| תאריך עברי | `@hebcal/core` |
| עיצוב | CSS מותאם אישית (`index.css`, ~1700 שורות), ללא ספריית UI חיצונית. Design tokens בתור CSS custom properties |
| פונט | Rubik (ראשי) + Plus Jakarta Sans (fallback) |
| אייקונים | Material Symbols Outlined (Google Fonts, טעון דרך `<link>`) |
| State management | React state מקומי (`useState`/`useEffect`) בכל עמוד בנפרד — **אין** ספריית caching (React Query/SWR וכו'). כל ניווט/mount טוען מחדש מה-API |
| Auth | Supabase Auth (session ב-localStorage), עטוף ב-`AuthContext` |

### מבנה תיקיות (`frontend/src`)

## 2. מערכת עיצוב (Design System)

הועתקה בפועל מ-`UX-UI/GEMINI` (שני קבצי HTML), עם טוקנים משותפים (CSS custom properties ב-`:root`) שמאפשרים "רי-טיוב" מלא של האפליקציה משינוי מקום אחד.

### פלטת צבעים

| טוקן | ערך | שימוש |
|---|---|---|
| `--bg` | `#f6f5fb` | רקע העמוד (**לא** לבן טהור בכוונה — ראו הערה למטה) |
| `--surface` / `--surface-white` | `#ffffff` | רקע כרטיסים |
| `--border-card` | `#eeeaf7` | מסגרת כרטיסים (טוקן ייעודי, נפרד מ-`--surface-highest` הכללי) |
| `--primary` | `#4f46e5` (אינדיגו) | הצבע הדומיננטי — כפתורים, אייקונים פעילים, לשונית פעילה |
| `--wordmark` | `#4a3372` | צבע ייעודי לוורדמארק "Giftly" בלבד (סגול כהה יותר, לא זהה ל-primary) |
| `--tertiary` / `--on-tertiary-container` | `#e11d48` (רוז) | אירועים דחופים, badges "בעוד X ימים" |
| `--secondary` / `--heritage-gold` | `#d97706` (ענבר) | הערות, badges מסוג "gold tier" |
| `--on-surface` | `#1e1b4b` | טקסט ראשי |
| `--on-surface-variant` | `#64748b` | טקסט משני |
| `--font` | `'Rubik', 'Plus Jakarta Sans', sans-serif` | |

**הערה חשובה שנלמדה תוך כדי עבודה:** רקע העמוד **חייב** להיות מעט שונה מלבן טהור (`#f6f5fb` ולא `#ffffff`), אחרת כרטיסים לבנים "נבלעים" ברקע ואין להם הפרדה חזותית — רק ה-border/shadow נותרים, וגם הם משתמשים בטוקנים אחרים במקומות שונים באפליקציה, כך שבלי ההבדל העדין הזה כל העיצוב נראה "שטוח" ולא מקצועי.

### צללים (Shadows)

| טוקן | ערך |
|---|---|
| `--shadow-1` | `0px 2px 8px rgba(79,70,229,0.06)` — לאלמנטים קטנים (כפתורי אייקון) |
| `--shadow-2` | `0px 8px 20px rgba(79,70,229,0.09)` — hover states |
| `--shadow-card` | `0px 10px 25px rgba(79,70,229,0.06)` — **מצב ברירת מחדל** של כרטיסים (לא רק hover!) — זה מה שיוצר תחושת "ריחוף" |
| `--shadow-celebratory` | `0px 10px 25px rgba(79,70,229,0.12)` — hover על כרטיסי אנשי קשר |

### רדיוסים

`--r-sm: 12px` · `--r-md: 18px` · `--r-lg: 24px` · `--r-xl: 28px` · `--r-full: 9999px`

### RTL

כל האפליקציה `dir="rtl"`. שימו לב: Flexbox/Grid הופכים כיוון אוטומטית תחת RTL — כשרוצים לשלוט בסדר החזותי בצורה מפורשת (למשל ניווט תחתון), צריך לשים לב לסדר ה-DOM ולא להשתמש ב-`flex-direction: row-reverse` בטעות (זה הפך להיות מקור לבאג חוזר בהיסטוריית הפיתוח).

## 3. ארכיטקטורת ניתוב ו-Shell

### מבנה הראוטים (`App.tsx`)

```
/login                     — LoginPage (ללא shell)
/setup                     — SetupPage (ProtectedRoute בלבד, ללא shell)
/approve-request           — ApproveRequestPage (ללא shell, נגישה גם ללא session — מגיעים מקישור מייל)
<Shell>                    — layout route: <AppShellLayout><Outlet/></AppShellLayout>
  /                         — DashboardPage   (SetupGuard)
  /contact/:id              — ContactPage      (SetupGuard)
  /profile                  — ProfilePage      (SetupGuard)
  /my-gifts                 — MyGiftsPage      (SetupGuard)
  /calendar                 — CalendarPage     (SetupGuard)
```

**נקודה ארכיטקטונית קריטית:** `AppShellLayout` (הכולל את הניווט התחתון/צדדי ואת ה-top bar) ממופה **פעם אחת** ברמת ה-`Shell` layout route, ולא בכל עמוד בנפרד. זה חשוב כי:
1. הוא נשאר "חי" (לא נטען מחדש) בין ניווטים — מה שמאפשר לאנימציית ה-tab הפעיל (`::before` שגדל מ-`scaleX(0.8)` ל-`scaleX(1)`) להתרחש בפועל, ולא רק "לקפוץ" למצב הסופי בכל mount מחדש.
2. שליפת האווטאר של המשתמש ב-top bar (`api.userProfile.me()`) קורית פעם אחת בלבד לכל סשן, ולא בכל קליק על ניווט.

עמודים שצריכים תצורה מיוחדת (למשל `MyGiftsPage` שרוצה `fullBleed`, או `DashboardPage` שמוסיף כפתור "היסטוריה" ל-top bar) עושים זאת דרך hook ייעודי:

```ts
useShellConfig({ fullBleed: true });
useShellConfig({ headerExtra: <button>...</button> });
```

זה עובד דרך `React.Context` (`ShellConfigContext`) — כל עמוד "מדווח" ל-Shell מה הוא צריך, וה-Shell מרנדר בהתאם.

### `SetupGuard`

עוטף כל עמוד שדורש פרופיל קיים. לוגיקה:
- אם המשתמש לא מחובר → redirect ל-`/login`.
- קורא ל-`GET /user-profile/me`.
- אם **404** אמיתי (אין עדיין פרופיל) → redirect ל-`/setup`.
- אם שגיאה **אחרת** (רשת/שרת) → מציג מסך "לא הצלחנו להתחבר לשרת, נסה שוב" (לא מפנה ל-setup בטעות! זה היה באג אמיתי שתוקן — כשל רשת חד-פעמי גרם למשתמשים קיימים "לאבד" את הפרופיל שלהם ולעבור תהליך רישום מחדש).

## 4. עמודים — פירוט מלא

### 4.1 LoginPage (`/login`)

**מטרה:** התחברות/הרשמה.

- לוגו: `logo-wordmark.png` — קרופ רחב (823×392px) מתוך `logo.png` המקורי (canvas ריבועי עם המון padding לבן סביב הוורדמארק). **אין** כותרת `<h1>Giftly</h1>` נפרדת — הלוגו עצמו הוא ה-wordmark המלא, וכפילות טקסט תוקנה.
- שני טאבים: התחברות / הרשמה (`.login-tabs`), עם pill רקע (`::before`) שגדל מ-`scaleX(0.8)` ל-`scaleX(1)` באנימציה של 0.8 שניות, עקומת easing `cubic-bezier(0.34, 1.56, 0.64, 1)` (overshoot קליל).
- שדות: אימייל, סיסמה (עם toggle הצגה/הסתרה), "שכחתי סיסמה".
- הרשמה → `supabase.auth.signUp` → הודעת "נשלח מייל אימות".
- התחברות → `supabase.auth.signInWithPassword` → ניווט ל-`/`.
- שגיאות מוצגות תחת הטאבים (`.form-error` / `.form-success`).

### 4.2 SetupPage (`/setup`)

**מטרה:** יצירת פרופיל ראשוני (רק פעם אחת, אחרי הרשמה).

טופס ארוך במספר section-ים (`.setup-section`):
1. **תמונת פרופיל** — `AvatarPicker` (מצויר / צללית / תמונה).
2. **פרטים בסיסיים** — שם מלא + כינוי ייחודי (`@username`, מנוקה אוטומטית לאותיות קטנות + underscore), מגדר (pills).
3. **מיקום ותקציר** — `LocationBirthFields` (תאריך לידה לועזי/עברי + עיר/מדינה) + Bio חופשי.
4. **תחומי עניין** — `TagInput` (מוזן AI-recommendations).
5. **הגדרות פרטיות** — 3 רמות: ציבורי / מחייב אישור (ברירת מחדל, מומלץ) / מוגן סיסמה (עם שדה קוד גישה + אימות).

שליחה → `POST /user-profile` → ניווט ל-`/`.

### 4.3 DashboardPage — "אנשי הקשר שלי" (`/`)

**זהו עמוד ה-Home הנוכחי.** מטרתו המוצהרת (כתובה תת-כותרת בעמוד עצמו): **"אירועים קרובים ששווה להתכונן אליהם"** — אבל בפועל הרשימה מוצגת לפי סדר טעינה מה-API (לא ממוינת לפי דחיפות אירוע), ואין קיצור דרך ישיר ל"מציאת מתנה". *(זו בדיוק הנקודה שדנו עליה לאחרונה ותוכננה לשינוי — ראו פרק 6.)*

**סעיפים:**
1. **בקשות ממתינות** (`.requests-section`, מוצג רק אם יש) — בקשות התחברות נכנסות (עם כפתורי אשר/דחה) ובקשות שהמשתמש שלח ועדיין ממתינות.
2. **כותרת** — "אנשי הקשר שלי" + תת-כותרת.
3. **כפתור FAB צף** (`.btn-fab`) — עיגול אינדיגו, `position: fixed`, פינה שמאלית תחתונה, אייקון "+" בלבד (ללא טקסט) — פותח מודל הוספת איש קשר.
4. **רשימת אנשי קשר** (`.contacts-list`) — grid רספונסיבי, כרטיס לכל איש קשר:
   - Badge צף מעל הכרטיס (גרדיאנט רוז) — מוצג **רק** אם יש אירוע תוך ≤6 ימים ("יום הולדת" וכו').
   - בתוך הכרטיס: אווטאר (56px) + שם — בצד ימין (RTL start). הודעת האירוע/ספירה לאחור — בצד שמאל.
   - **הוסר בכוונה:** תגית "יחס" (חבר/משפחה) ושם המשתמש המקושר (@nickname) — הוחלט שזה מידע לא רלוונטי למבט חטוף.
   - צבע ה-badge/הספירה משתנה לפי דחיפות: `soon` (רוז, ≤6 ימים) / `gold` (ענבר, ≤45 ימים) / ברירת מחדל.
5. **מודל הוספת איש קשר** (`.modal-overlay`) — חיפוש משתמש קיים ב-Giftly לפי כינוי/מייל (מקשר פרופילים — כשמקושר, שדות רבים מוסתרים כי הם יגיעו מהפרופיל המקושר), או מילוי ידני מלא (שם, יחס, תחומי עניין, מגדר, תאריך לידה, מיקום, מצב משפחתי/ילדים/דת, הערות). אם המשתמש המקושר מוגן בסיסמה — נדרש קוד גישה.
6. **פאנל היסטוריה** (`.panel`, side drawer) — נפתח מכפתור ב-top bar (`headerExtra` דרך `useShellConfig`), מציג את כל ה-recommendations שנוצרו אי-פעם עבור כל אנשי הקשר.

### 4.4 ContactPage (`/contact/:id`)

**המטרה המרכזית של האפליקציה קורית כאן.** עמוד "בנטו גריד" (2 עמודות בדסקטופ, קורס לעמודה אחת מ-900px).

**Header:** כפתור חזרה (chevron, שמאל=חזרה בעמוד RTL) + כפתור עריכה (עיפרון) — שני `icon-btn` עגולים.

**עמודה שמאלית — כרטיס פרופיל (`profile-card-head`):**
- אווטאר גדול (88px) עם badge "יחס" (חבר/וכו') **חופף** לתחתית העיגול (position: absolute, ממורכז) — לא טקסט נפרד מתחת לשם.
- אם לא מקושר לפרופיל אמיתי → כפתור עריכת אווטאר קטן.
- שם מלא.
- אם מקושר לפרופיל Giftly אמיתי → badge "פרופיל מקושר: @nickname".
- **Meta pills** (`.meta-pills`) — שורת pills עם אייקונים: מגדר, גיל, מיקום, מצב משפחתי, ילדים, דת (כל שדה קיים בלבד).
- Bio (`.bio-text`) — עם קו מקווקו מעליו.
- תגי תחומי עניין (`.tags`).
- Note box (`.notes-box`) — רקע ענבר, אייקון "sticky_note_2", מוצג רק אם יש הערה.
- כפתור מעבר למצב עריכה (מוזז ל-header — הלחיצה על העיפרון ב-top פותחת/סוגרת טופס עריכה מלא inline, לא modal).

**עמודה ימנית — אירועים + AI:**
- **סקשן אירועים** — כותרת + כפתור "אירוע חדש". `EventForm` מוצג inline כשפותחים/עורכים. אירועים מוצגים ב-**קרוסלה אופקית** (`.events-scroll`, scroll-snap-x) — כרטיס לכל אירוע (170px רוחב קבוע): badge (אייקון + "בעוד X ימים!" אם דחוף, אחרת סוג האירוע), כותרת, תאריך, תקציב (אם הוגדר), footer עם מספר ימים גדול + כפתור עריכה. לחיצה על כרטיס אירוע **בוחרת** אותו (`selected`) — זה מסנן את ההמלצות למטה לפי טווח התקציב של האירוע הזה.
- **AI Recommendations banner** (`.ai-banner`) — כרטיס גרדיאנט אינדיגו→סגול, בולט חזותית מכל שאר העמוד. בפנים: כותרת + subtitle (או chip "מסונן לפי תקציב X–Y ₪" אם נבחר אירוע) + כפתור "ייצר המלצות" (מושבת אם לא נבחר אירוע). מתחת: `RecommendationCarousel` — קרוסלה אופקית של כרטיסי מתנה (`.tag-card`, 250px קבוע), כל כרטיס: תמונה/גרדיאנט קטגוריה, % התאמה (אם קיים), קטגוריה, כותרת, תיאור, מחיר, כפתור "חיפוש בגוגל" (`google.com/search?q=...`).

**⚠️ זו בדיוק הנקודה שהועלתה לדיון האחרון:** כדי להגיע להמלצה, המשתמש צריך: לזכור מי צריך מתנה → לגלול ברשימה האלפביתית → להיכנס לאיש קשר → לגלול למטה עד לסקשן ה-AI → לגלול **הצידה** בקרוסלה. תוכנן (טרם בוצע) מסך ייעודי חדש לזרימה הזו — ראו פרק 6.

### 4.5 ProfilePage — עריכת פרופיל אישי (`/profile`)

זהה במבנה ל-SetupPage אך לעריכת הפרופיל הקיים של המשתמש עצמו (`PATCH /user-profile`). כולל את כל אותם השדות (אווטאר, שם/כינוי, מגדר, מיקום/תאריך לידה, תחומי עניין, Bio, מצב משפחתי/ילדים/דת, רמת פרטיות). כפתורי "שמירת שינויים" / "ביטול" (חזרה ל-`/`).

### 4.6 CalendarPage (`/calendar`)

שני חלקים עיקריים (`.cal-body`, מתקפל לעמודה אחת במובייל):
- **שמאל:** לוח שנה חודשי אינטראקטיבי (grid 7 עמודות) עם ניווט חודש קודם/הבא, נקודת צבע לפי סוג אירוע בכל יום שיש בו אירוע, יום נבחר מודגש. בבחירת יום — מוצגת רשימת האירועים של אותו יום.
- **ימין:** "אירועים קרובים" — 10 האירועים הקרובים ביותר על פני **כל השנה** (לא רק החודש הנוכחי), מקובצים לפי תאריך, כל אחד עם כפתור "מצא מתנה" שמנווט ל-`/contact/:id` (זה אחד ממקומות הכניסה הקיימים לזרימת מציאת המתנה, בנוסף לרשימת אנשי הקשר).
- תמיכה מלאה בתאריכים עבריים (`@hebcal/core` דרך `hebrewDate.ts`) — אירוע שמוגדר בלוח עברי מוצג גם עם badge "תאריך עברי".

### 4.7 MyGiftsPage — "הצעות בשבילי" (`/my-gifts`)

**עמוד ה"מנוע" של המלצות אישיות** — feed אנכי בסגנון TikTok, כרטיס אחד = כל המסך (`scroll-snap-type: y mandatory`, `scroll-snap-stop: always` — מונע "דילוג" על יותר מכרטיס אחד בגלילה חזקה).

לכל כרטיס (`.mg-feed-item`): תמונה מלאה (או גרדיאנט קטגוריה כברירת מחדל — `image_url` עדיין לא מאוכלס ע"י ה-backend), scrim כהה מלמטה, ותוכן: badge ("הצעה בשבילך" / "דורג ✓"), **כותרת עם אנימציית reveal** (clip-path sweep), **תיאור עם fade-in** — האנימציות האלו **מתרעננות בכל פעם שהכרטיס הופך לפעיל** (לא רק פעם אחת ב-mount — נעשה דרך `key` שמשתנה ב-React על בסיס `IntersectionObserver`).

- דירוג (`StarRating`, 1-5 כוכבים) — בלחיצה נשלח `PATCH /self-recommendations/:id/rate`. **דירוג 5 כוכבים מפעיל אפקט חגיגה** (חלקיקים אנימטיביים עפים למעלה — קונפטי).
- קישור "חפש ב-Google" (אם יש `search_query`).
- כרטיס אחרון קבוע — "ראית הכל!" עם כפתור רענון (`POST /self-recommendations/generate`).
- **נקודות התקדמות** (`.mg-feed-dots`) — עמודת נקודות בצד, מציגות את המיקום הנוכחי בפיד. מרונדרות **כ-sibling** של אזור הגלילה (לא בתוכו!) כדי שלא "יגללו החוצה" עם התוכן.
- בדסקטופ בלבד: חצי ניווט למעלה/למטה (`.mg-feed-nav`) + הכרטיס מוצג במסגרת (frame) ולא edge-to-edge.

**חשוב לפי החלטה מפורשת בשיחה האחרונה:** לשונית זו **נשארת** בניווט התחתון כרכיב עצמאי — היא "המנגנון" שהכי חשוב שהמשתמשים ימשיכו להשתמש בו כדי לדרג מתנות ולהזין את מנוע ההמלצות. שום עמוד/פיצ'ר עתידי לא אמור "לבלוע" אותה.

### 4.8 ApproveRequestPage (`/approve-request`)

עמוד "נחיתה" סטטי בלבד — נגיש **ללא** session (לא עטוף ב-Shell/SetupGuard), כי מגיעים אליו מקישור שנשלח במייל. קורא query params (`result=approved|rejected`, `error=notfound|...`) ומציג הודעת הצלחה/כישלון/שגיאה בהתאם, עם כפתור "לדף הבית". *(האישור/דחייה עצמם קורים ב-backend, לא כאן — זהו רק מסך תוצאה.)*

## 6. מודל נתונים (טיפוסי Frontend, `types/index.ts`)

- **`UserProfile`** — הפרופיל של משתמש רשום (שם, כינוי ייחודי, אימייל, תחומי עניין, Bio, תאריך לידה, מיקום, מגדר, רמת פרטיות, אווטאר).
- **`Contact`** — איש קשר בבעלות משתמש. יכול להיות **עצמאי** (כל השדות ממולאים ידנית) או **מקושר** (`linked_user_id` + `user_profile` populated — במקרה כזה שדות רבים "נגזרים" מהפרופיל המקושר בעדיפות, ראו `displayName`/`displayBio` וכו' ב-ContactPage).
- **`ContactRequest`** — בקשת חיבור בין שני משתמשים רשומים (למקרה שהפרטיות מחייבת אישור).
- **`Event`** — אירוע של איש קשר (סוג, תאריך [לועזי/עברי], ימי תזכורת, טווח תקציב).
- **`Recommendation`** — המלצת מתנה (כותרת, תיאור, מחיר משוער, קטגוריה, שאילתת חיפוש, ציון התאמה, `image_url` **עדיין לא מאוכלס ע"י ה-backend** — כרגע תמיד fallback לגרדיאנט לפי קטגוריה).
- **`GiftHistory`** — טיפוס קיים אך לא בשימוש פעיל ב-UI הנוכחי.

## 7. שכבת API (`lib/api.ts`)

Wrapper דק סביב `fetch`, `API_BASE = import.meta.env.VITE_API_URL ?? ''` (ריק בפיתוח מקומי — Vite proxy מפנה `/api` ל-`localhost:3001`; ב-production זו כתובת ה-backend הנפרד ב-Render).

כל קריאה מוסיפה `Authorization: Bearer <supabase access token>` אוטומטית. שגיאות נזרקות כ-`ApiError` (עם `status` — מאפשר להבחין בין 404 אמיתי לשגיאת רשת/שרת, קריטי ל-`SetupGuard`). תגובה ריקה/פגומה על סטטוס 2xx (cold-start של Render וכו') נתפסת ומוצגת כהודעת "נסה שוב" ידידותית במקום שגיאת JavaScript גולמית.

Namespaces: `userProfile`, `contacts`, `events`, `gifts`, `recommendations`, `selfRecommendations`, `contactRequests`.

**אין client-side caching** — כל `useEffect` שקורא ל-API רץ מחדש בכל mount של עמוד. זוהה כפוטנציאל לשיפור (ראו TODO בזיכרון — הצעה ל-TanStack Query/SWR, טרם החל).

## 9. תכנון פתוח שטרם מומש (מהשיחה האחרונה — לא בקוד עדיין!)

זהו סיכום ההחלטות שהתקבלו בדיון התכנון האחרון, **טרם יושמו**:

1. **לשונית "Home" חדשה ונפרדת** (לא מיזוג עם `אנשי קשר` או `הצעות בשבילי`) — עם אייקון מתנה שיהפוך בעתיד ללוגו הרשמי של Giftly. תוכן:
   - "אירועים ששווה להתכונן אליהם" — סקציה שמציגה אנשי קשר עם אירוע קרוב, ממוינים לפי דחיפות (בניגוד למצב הנוכחי שבו ה-Dashboard מבטיח את זה בכותרת אך לא מספק בפועל).
   - תזכורת אם יש הצעות חדשות ל"הצעות בשבילי" שעדיין לא נצפו/דורגו.
2. **`אנשי קשר` הופך לרשימה טהורה** (עיון/חיפוש/הוספה) — ללא אחריות על "מה דחוף עכשיו".
3. **`הצעות בשבילי` נשארת לשונית עצמאית** בניווט התחתון — **לא** נבלעת ב-Home. הנימוק המפורש: זהו הערוץ הכי חשוב לשמור על מעורבות משתמש בדירוג מתנות (מזין את מנגנון ההמלצות).
4. **מסך ייעודי חדש למציאת מתנה לחבר** — כרגע, מלחיצה על "מצא מתנה" (מה-Dashboard/Calendar/Contact) מגיעים ל-`ContactPage` שבו הקרוסלה אופקית וקבורה מתחת לפרופיל+אירועים. הוחלט: לחיצה על "חפש מתנה עבור X" צריכה להוביל **לעמוד נפרד**, בהשראת UX ה-feed האנכי הקיים ב-`MyGiftsPage` (swipe + rate), כדי שלא יידרש גלילה **הצידה** כדי להגיע להמלצה. עדיין לא הוחלט: route מדויק, האם משתפים קוד עם `MyGiftsPage`/`FeedCard`, איך דירוג "עבור חבר" נשמר (הוזכר: מקומית בלבד, אצל המשתמש, לא משותף).
5. **"קבוצות למתנה"** — פיצ'ר עתידי, טרם תוכנן ברמת מנגנון (כנראה סינון/קיבוץ מעל אנשי קשר ולא לשונית נפרדת, כדי לא "להתחרות" על מקום עם Home).
